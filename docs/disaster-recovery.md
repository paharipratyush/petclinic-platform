## RTO and RPO Targets

| Component | RPO | RTO |
|-----------|-----|-----|
| RDS MySQL (prod) | 24 h (daily automated backup) | 1–2 h (restore from snapshot) |
| EKS workloads | 0 (stateless, re-deployed from Git) | 30 min (fresh cluster + ArgoCD sync) |
| ECR images | 0 (images rebuilt from source) | 1 h (CI rebuild) |
| Terraform state | Near-zero (S3 versioning + DynamoDB) | 15 min (restore from S3 version) |
| Secrets Manager secrets | N/A (replicated by AWS) | 5 min (re-create from runbook) |

> **Dev environment:** backup_retention_period = 0 (free-tier constraint). Dev has no RPO guarantee — data loss is acceptable. See runbook: [Free-Tier RDS Backup Deviation](runbook.md#free-tier-rds-backup-deviation).

## What Is Backed Up

### RDS MySQL (prod only)

- **Automated daily snapshots** — retention: 30 days, stored by AWS in eu-central-1
- **Final snapshot on deletion** — `skip_final_snapshot = false`; snapshot name: `petclinic-prod-mysql-final`
- **Deletion protection** — `deletion_protection = true` prevents accidental `terraform destroy`

### Terraform State

- **S3 versioning enabled** on the state bucket (`petclinic-terraform-state`)
- Every `terraform apply` creates a new S3 object version; previous versions are retained indefinitely
- DynamoDB lock table prevents concurrent writes that could corrupt state

### Application Configuration

- All infrastructure is defined in Git — the repo IS the backup
- Helm values (including image tags) are committed to Git after every CI build
- No mutable application state outside RDS

### AWS Secrets Manager

- Secrets are managed by AWS with cross-AZ replication within eu-central-1
- Secret versions are retained by AWS until the recovery window expires
- RDS password is auto-generated by Terraform (stored in Secrets Manager, not in state)
- Grafana admin password is provided at deploy time via `TF_VAR_grafana_admin_password`

## Failure Scenarios

### Scenario 1: RDS MySQL failure

**Symptoms:** `customers-service`, `visits-service`, `vets-service` pods show DB connection errors.

**Recovery steps:**

```bash
# 1. Check RDS instance status
aws rds describe-db-instances \
  --db-instance-identifier petclinic-prod-mysql \
  --query 'DBInstances[0].DBInstanceStatus'

# 2. If instance is in "failed" state, restore from latest snapshot
SNAPSHOT=$(aws rds describe-db-snapshots \
  --db-instance-identifier petclinic-prod-mysql \
  --query 'reverse(sort_by(DBSnapshots, &SnapshotCreateTime))[0].DBSnapshotIdentifier' \
  --output text)

aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier petclinic-prod-mysql-restored \
  --db-snapshot-identifier "$SNAPSHOT" \
  --db-instance-class db.t4g.micro \
  --no-multi-az

# 3. Wait for restore to complete (~15 min)
aws rds wait db-instance-available \
  --db-instance-identifier petclinic-prod-mysql-restored

# 4. Update Terraform to point to restored instance (rename or taint)
# See runbook for Terraform import procedure
```

**Verify:** Connect to restored instance, check table counts match pre-failure snapshot.

**Rollback:** If restore fails, use the prior snapshot (list with `aws rds describe-db-snapshots`).

### Scenario 2: EKS Cluster Failure

**Symptoms:** `kubectl` commands fail, ArgoCD UI unreachable, all workloads down.

**Recovery steps:**

```bash
# 1. Verify cluster state
aws eks describe-cluster --name petclinic-prod-eks \
  --query 'cluster.status'

# 2. If cluster is FAILED or DELETING, rebuild from Terraform
cd terraform/environments/prod
terraform plan -out plan.out
terraform apply plan.out  # Re-creates cluster; all state is in Git

# 3. Re-bootstrap the cluster after Terraform apply
kubectl apply -f k8s/argocd/install/namespace.yaml
kubectl apply -f k8s/argocd/install/install.yaml

# Wait for ArgoCD to be ready
kubectl wait --for=condition=available deployment/argocd-server \
  -n argocd --timeout=300s

# 4. Apply base manifests
kubectl apply -f k8s/base/namespaces/
kubectl apply -f k8s/base/observability/namespace.yaml
kubectl apply -f k8s/base/external-secrets/cluster-secret-store.yaml
kubectl apply -f k8s/base/external-secrets/

# 5. Register ArgoCD applications — ArgoCD will sync workloads automatically
kubectl apply -f k8s/argocd/applications/prod/
```

**Verify:** All ArgoCD applications show "Synced / Healthy" within 10 minutes.

### Scenario 3: ECR Repository Loss

**Symptoms:** Image pulls fail with `pull access denied` or 404 errors.

**Recovery steps:**

```bash
# 1. Recreate ECR repos via Terraform
cd terraform/environments/prod
terraform plan -target=module.ecr -out plan.out
terraform apply plan.out

# 2. Trigger full CI rebuild to push all images
# Go to the APPLICATION REPO FORK → GitHub Actions → build-push.yml → Run workflow
# OR manually rebuild and push using the platform repo script:
REGISTRY=533267262133.dkr.ecr.eu-central-1.amazonaws.com/petclinic-prod
bash scripts/ecr-login.sh prod
bash scripts/build-push.sh prod all

# 3. Verify images are present in ECR
aws ecr describe-images \
  --repository-name petclinic-prod/api-gateway \
  --query 'imageDetails[0].imageTags'
```

**Verify:** ArgoCD reports all applications as Synced after images are available.

### Scenario 4: Terraform State Corruption

**Symptoms:** `terraform plan` errors with "state file locked" or "inconsistent state".

**Recovery steps:**

```bash
# 1. Check for stale DynamoDB lock
aws dynamodb scan \
  --table-name petclinic-terraform-locks \
  --filter-expression "begins_with(LockID, :prefix)" \
  --expression-attribute-values '{":prefix": {"S": "petclinic/prod/"}}' \
  --query 'Items[*].LockID'

# If stale lock found (no active terraform process running):
aws dynamodb delete-item \
  --table-name petclinic-terraform-locks \
  --key '{"LockID": {"S": "petclinic/prod/terraform.tfstate-md5"}}'

# 2. If state file is corrupted, restore from S3 version
BUCKET=petclinic-terraform-state

# List available versions
aws s3api list-object-versions \
  --bucket "$BUCKET" \
  --prefix petclinic/prod/terraform.tfstate \
  --query 'Versions[?IsLatest==`false`].[VersionId,LastModified]' \
  --output table

# Restore a specific version (replace VERSION_ID with the chosen one)
aws s3api copy-object \
  --copy-source "${BUCKET}/petclinic/prod/terraform.tfstate?versionId=VERSION_ID" \
  --bucket "$BUCKET" \
  --key petclinic/prod/terraform.tfstate

# 3. Run terraform plan to verify state is consistent
cd terraform/environments/prod
terraform plan
```

### Scenario 5: Full Region Outage

eu-central-1 is the only region for this project. A full regional outage means complete service unavailability until the region recovers.

**Recovery actions (region restored):**

1. Verify Terraform state is intact: `aws s3 ls s3://petclinic-terraform-state/petclinic/prod/`
2. Re-run `terraform plan` to detect any AWS-side drift
3. Apply any drift: `terraform apply plan.out`
4. Verify EKS cluster is reachable and all pods are Running
5. Verify RDS is available; if automated failover occurred, check new endpoint: `aws rds describe-db-instances`

**Prevention:** This is a learning project using a single-AZ, single-region setup. For real production: add Multi-AZ RDS, consider Route 53 health checks, and plan for cross-region EKS.

## Backup Verification

Run quarterly or after any infrastructure change:

```bash
# 1. Verify RDS automated backups exist (prod only)
aws rds describe-db-snapshots \
  --db-instance-identifier petclinic-prod-mysql \
  --snapshot-type automated \
  --query 'DBSnapshots[0].{ID:DBSnapshotIdentifier,Created:SnapshotCreateTime,Status:Status}' \
  --output json

# 2. Verify S3 state bucket versioning is enabled
aws s3api get-bucket-versioning \
  --bucket petclinic-terraform-state

# 3. Verify DynamoDB lock table exists
aws dynamodb describe-table \
  --table-name petclinic-terraform-locks \
  --query 'Table.TableStatus'

# 4. Verify Secrets Manager secrets are accessible
aws secretsmanager get-secret-value \
  --secret-id petclinic/prod/rds-credentials \
  --query 'SecretString' | jq -r . | jq 'keys'
```

## Infrastructure Rebuild Procedure

Use this when rebuilding from scratch after a catastrophic loss.

### Prerequisites

- AWS credentials with admin access
- `terraform`, `kubectl`, `helm`, `argocd` CLI tools installed
- `CLOUDFLARE_API_TOKEN` set in environment
- Secrets ready: `TF_VAR_openai_api_key`, `TF_VAR_grafana_admin_password`, `TF_VAR_budget_alert_email`, `TF_VAR_domain_name`

### Step 1: Bootstrap state backend

```bash
bash scripts/bootstrap-state.sh {env}
```

### Step 2: Apply Terraform

```bash
cd terraform/environments/{env}
terraform init
terraform plan -out plan.out
terraform apply plan.out
```

### Step 3: Configure kubectl

```bash
aws eks update-kubeconfig \
  --region eu-central-1 \
  --name petclinic-{env}-eks
```

### Step 4: Install cluster add-ons

```bash
bash scripts/up.sh {env}
# This installs: ESO, LB Controller, Karpenter, observability stack
```

### Step 5: Apply base K8s manifests

```bash
kubectl apply -f k8s/base/namespaces/
kubectl apply -f k8s/base/observability/namespace.yaml
kubectl apply -f k8s/base/external-secrets/cluster-secret-store.yaml
kubectl apply -f k8s/base/external-secrets/
kubectl apply -f k8s/base/network-policies/
kubectl apply -f k8s/base/observability/network-policies.yaml
```

### Step 6: Install ArgoCD

```bash
kubectl apply -f k8s/argocd/install/namespace.yaml
kubectl apply -f k8s/argocd/install/install.yaml
kubectl wait --for=condition=available deployment/argocd-server \
  -n argocd --timeout=300s
kubectl apply -f k8s/argocd/argocd-rbac-cm.yaml
kubectl apply -f k8s/argocd/appproject-dev.yaml
kubectl apply -f k8s/argocd/appproject-prod.yaml
```

### Step 7: Register ArgoCD applications

```bash
kubectl apply -f k8s/argocd/applications/{env}/
# ArgoCD auto-syncs dev; prod requires manual sync in ArgoCD UI
```

### Step 8: Verify

```bash
bash scripts/smoke-test.sh {env}
```
